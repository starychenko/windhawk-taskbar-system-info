# Taskbar System Info 1.7.0

Taskbar System Info now adapts its contents to both the free width and the height
of the taskbar. A low panel can keep a readable widget by using fewer details or
one row. No small-taskbar setting is needed.

This fixes the small-taskbar regression reported in
[#6](https://github.com/starychenko/windhawk-taskbar-system-info/pull/6).
Version 1.6.0 required at least 85% of the normal 38-DIP widget height, so a
30-DIP panel could hide the widget. The new solver can retain a compact two-row
layout on that panel while keeping the main font at least 9 logical pixels.

Thanks to [@gylangsatria](https://github.com/gylangsatria) for identifying the
regression and contributing a proposed fix and tests in #6. This release uses
automatic layout selection instead of the proposed `shortTaskbar` switch and
its lower 8-DIP text limit.

## Four automatic layouts

| Layout | Visible readings |
| --- | --- |
| **Full, two rows** | CPU/GPU usage, temperatures and history graphs; RAM/VRAM percentages, used/total capacity and bars. |
| **Without graphs, two rows** | All numeric readings and memory bars. |
| **Compact, two rows** | CPU/GPU usage and temperatures; RAM/VRAM percentages. |
| **Compact, one row** | The same essential readings, ordered CPU, GPU, RAM, VRAM. |

The mod measures visible taskbar controls, free gaps and the configured font.
Opening more apps, changing Search or Widgets, changing the font, or using a
taskbar with different dimensions can select another layout. There is no fixed
screen-resolution threshold. The examples above use 30-DIP and 20-DIP heights
for the compact layouts; these are examples, not universal switching points.
A single row needs more width than compact two rows and helps when height is
scarce.

The normal full view is tried first, including its existing readable shrinking.
If that cannot fit or its fixed cells cannot hold the configured font, the solver
tries a measured full view, no graphs, compact two rows and compact one row at
the configured font size. Two-row layouts remove vertical gaps before reducing
row height. Compact layouts can also shrink, but the main font stays at least
9 logical pixels. If no readable layout fits, the normal widget hides and an
invalid move target turns red.

The full view returns automatically when room becomes available. Hidden graphs
keep collecting timestamped history and return at its actual age. Automatic
adaptation preserves the configured width, offset and saved position.
**Widget width** remains a preference for the full view; it does not limit the
measured width of a readable adaptive layout that fits in the available space.
This also fixes a low-panel case where Verdana at size 9 and width preference
330 could hide the widget despite a wider usable gap.

## Dragging, placement and saved positions

The live move preview uses the destination taskbar's free space, height and DPI.
It can change between one and two rows while dragging, keeping the grabbed point
aligned with the cursor. Text, graphs and memory bars continue to update.

**Ctrl+Alt+M**, **Enter**, **Esc** and **Home** keep their existing behavior.
Enter checks the destination layout again before applying and saving the move.
The normal widget stays transparent and click-through; the move preview has a
glass background only while dragging. A red position cannot be saved.

Full size and readability take priority over proximity. If shrinking is needed,
the widest usable gap is preferred before distance. Saved horizontal positions
use the available travel width of the actual layout, so reloading a confirmed
position preserves its layout and placement. Reserve-space verification also
uses the arranged adaptive widget. Failed confirmation or persistence restores
the previous state.

There are still **29 settings**. No settings migration is required. Existing
per-display profiles keep their version-1 format, and the documented monitor,
offset and reset priorities remain in place.

## Stale readings and temperature providers

A stopped metrics collector no longer leaves old readings displayed as current.
After five seconds or three configured update intervals, whichever is longer,
the readings become unavailable. Memory fills and alerts clear, history keeps
aging, and the next fresh publication restores the readings. This also applies
while moving the widget. Forced redraws and move verification do not refresh old
sample timestamps or make stalled history look new.

HWiNFO Shared Memory now checks the publication timestamp before copying sensor
tables. A frozen or already stale publication is rejected. The freshness limit
allows three HWiNFO polling periods plus two seconds, with a five-second minimum.
Automatic mode tries the remaining providers when that source expires and
recovers when fresh polling returns.

Gadget Registry readings expire after **60 seconds without a key write**.
The key's timestamp is checked before and after reading to reject a publication
that changes during the read. Registry has no polling heartbeat, and HWiNFO can
skip writes when exported values stay unchanged. An unchanged key can therefore
expire while HWiNFO is still running. Use Shared Memory when constant temperature
readings must remain available. A fresh Registry write restores the readings
even when the selected temperature value is unchanged.

Unavailable temperatures show `--°C`. An unavailable provider does not stop the
independent CPU, GPU or memory readings. HWiNFO remains optional.

## GPU counter recovery

Matching GPU engine values with invalid `CStatus` no longer count as idle 0%.
Missing engine instances can mean idle only when the selected adapter's memory
counter still supplies a valid reading. Invalid or missing readings otherwise
remain unavailable.

After three consecutive samples with invalid matching engine values and working
memory, the worker starts a separate fresh-query probe. Baseline and rate samples
are collected on different worker ticks, at least one update interval apart.
Only a valid fresh rate replaces the old query; probes are limited to one per
minute. This avoids discarding the current query before a replacement works.
CPU and RAM remain independent while GPU counters establish a new baseline.

## Documentation and development

The repository README and embedded Windhawk guide now explain every adaptive
layout, when it is selected, hide/restore behavior and destination-aware dragging.
The gallery contains **14 renders**, including six new adaptive examples in dark
and light themes. Existing normal, move, invalid-position, large-text and contrast
examples have been refreshed.

The images use the actual XAML widget and native move renderer, with readings
from a workstation snapshot: Ryzen 9 5900X, 64 GB RAM and RX 7900 XTX with 24 GB
VRAM. The snapshot shows CPU 4% at 47°C, GPU 0% at 37°C, about 23.3/64 GiB RAM
and 2.3/24 GiB VRAM. History is illustrative, and the images are isolated renders.
Maximum-value stress renders remain separate from the documentation gallery.
The contrast palette is simulated without changing Windows settings.

VS Code now has a portable Windhawk Clang/C++23 IntelliSense configuration.
The Python validator has explicit scalar/option types for strict checking, and
the standalone metrics test defines `NOMINMAX` to avoid Windows macro collisions.

## Compatibility and remaining live checks

The source targets **Windows 11 x86-64** and is built with Windhawk **1.7.3**.
ARM64 is a cross-build check; ARM64 hardware has not been tested and the mod's
metadata still targets x86-64.

The automated checks use isolated XAML/Win32 fixtures and synthetic provider
failures, plus read-only live Windows provider reads. They do not prove the
contributor's physical Taskbar Styler preset, a real graphics-driver reset or
physical transfers between monitors with different DPI and taskbar heights.
Live Explorer checks remain pending for top/bottom placement, left/center
alignment, taskbar controls and clicks, disconnect/reconnect, restart persistence
and unloading during editing. Separately hosted third-party taskbar elements
may need their own compatibility work.

The installed Explorer mod is not replaced as part of release qualification.
See the [placement verification record](https://github.com/starychenko/windhawk-taskbar-system-info/blob/v1.7.0/docs/placement-verification-2026-10-04.md)
for the earlier evidence and the live-check boundaries.

## Install or update

Download **taskbar-system-info.wh.cpp** from this release. In Windhawk, create a
new mod, replace its source with this file, compile and enable it. To update an
existing local copy, replace its source in that mod's editor and compile it.
The download includes the guide, settings and implementation.
